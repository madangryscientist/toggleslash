# Architecture

This page records the design the later tickets build on. It is a decision record, not a description
of what exists: today `apps/server` migrates its database, answers `GET /health` and serves the admin API (SDK keys, scoped API tokens, projects, environments, flags, targeting, segments and the audit trail) and the SDK read API (the ruleset, its live-update stream and server-side evaluate), and usage counts (`POST /sdk/v1/events`, the per-flag usage read and `lastEvaluated`), and nothing else. Where a section says
"will", the code arrives in its own ticket.

## Who owns what

**The C# server (`apps/server`) owns all flag data and the API.** It is an ASP.NET Core minimal API
on .NET 10. TypeScript stays for the engine, the SDKs, the CLI, the dashboard and the site.

| Piece | Language | Role |
| --- | --- | --- |
| `apps/server` | C# | flag data, the HTTP API, auth, evaluation for clients that ask the server |
| `packages/engine` | TypeScript | flag evaluation, for TypeScript SDKs |
| `packages/sdk` | TypeScript | the server-side SDK: ruleset, stream, local evaluation, usage counts (see [`sdk.md`](sdk.md)) |
| `packages/sdk-otel` | TypeScript | an SDK hook that puts each evaluation and the ruleset hash on the active OpenTelemetry span (see [`tracing.md`](tracing.md)) |
| `packages/cli` | TypeScript | the `toggleslash` command; calls the admin API (`config`, `projects`, `envs`, `flags`, `keys`, `tokens`) |
| `apps/web` | TypeScript | the dashboard; calls the server |
| `apps/site` | TypeScript | the marketing site, prerendered |

## Storage

SQLite through EF Core, in `apps/server/ToggleSlash.Server/Data`. The path comes from the
`TOGGLESLASH_DB_PATH` environment variable; the default is `toggleslash.db`, relative to the
server's working directory, and `*.db` is git-ignored. Migrations are generated by `dotnet ef` (never
hand-written) and are additive. Postgres is a later option, not a goal of the first version.

**One self-hosted process owns one file.** The server applies pending migrations at startup, all of
them in one transaction, so a failure leaves the file as it was and the server does not start.
EF takes no migration lock inside that transaction; SQLite's write lock does the job. A second process
starting on the same file waits for the first, then finds nothing pending.

The tables are `projects`, `environments`, `flags`, `flag_environment_configs`, `segments`,
`api_keys`, `admin_tokens`, `audit_events`, `flag_usage_daily` and `ruleset_snapshots`. JSON from `docs/evaluation.md` (variations, targets,
rules and so on) is stored as text. A flag's `salt` is on `flags`, because the spec does not list it as
per-environment. `segments` and `flag_environment_configs` do not stop a row pointing across projects
or environments; that is the API's check to make, and the targeting routes make it (below).

## Auth

`Authorization: Bearer <token>` on every request that is not `/health` or `/openapi/v1.json`.

- **Admin:** a bootstrap admin token is read from the `TOGGLESLASH_ADMIN_TOKEN` environment
  variable and compared in constant time. It is never stored in the database or the tree, and the
  server never generates one. Unset or blank, every admin route answers 503 and names the variable,
  whatever the request sent; the rest of the server runs as usual.
- **SDK keys:** one set per environment, managed by the admin at
  `/api/v1/projects/{project}/environments/{env}/keys` (`POST` creates, `GET` lists, `DELETE .../{id}`
  revokes). The server stores only the SHA-256 hash of a key and a display prefix; the plain key is
  returned once, by the `POST`. A key is 32 bytes from a CSPRNG, so a plain hash is enough.
- **Scoped API tokens:** for Terraform and CI, which should not hold the root token. A token belongs to one
  project, is `read` or `write`, and always expires (1 to 365 days from creation; there is no other choice). It looks like
  `fs_admin_<64 hex>` and is stored like an SDK key: the SHA-256 hash and a display prefix, the plain token returned
  once. The root token manages them at `/api/v1/projects/{project}/tokens` (`POST` creates, `GET` lists all of them,
  expired and revoked too, `DELETE .../{id}` revokes). An expired or revoked token is the same 401 as an unknown one
  and counts as an auth failure.
- There are no user accounts yet.

The two kinds of SDK key:

| Kind | Looks like | Policy | Who holds it | What it may do |
| --- | --- | --- | --- | --- |
| server | `fs_server_<64 hex>` | `server-key` | a backend you run | read the ruleset, follow its stream, evaluate locally and report usage counts |
| client | `fs_client_<64 hex>` | `client-key` | a browser or a mobile app, so assume it is public | ask the server to evaluate and report usage counts; **never** read the ruleset or its stream |

The kind that counts is the one stored with the key; the text in front is for people and secret
scanners. The ruleset and stream routes are gated on `server-key`; the evaluate and events routes on `sdk-key`, which is either kind.

The policies are `admin`, `server-key` and `client-key`, and none includes another: an admin credential
is not an SDK key, and neither kind of key passes for the other. (`sdk-key` is not a third kind of key:
it is the policy of a route that takes a server or a client key.) All these credentials go through one
authentication scheme, so **401** means the token is missing, malformed, wrong or revoked and **403**
means it is valid but not for this route. A 401 does not say which of those it was. **429** means a limit,
[below](#rate-limits). **413** is a body over 1 MiB (128 KiB on `events`), and **504** (`request_timeout`) a request
that ran past 30 seconds; both are in [`self-hosting.md`](self-hosting.md#headers-body-size-and-timeouts).

**What a scoped token may reach** is decided in one place, the `admin` policy (`ServerAuth.MayUseAdminRoute`), and every
admin route stays on that policy. The root token passes everywhere. A scoped token passes only when all of these hold:

- The route's `{project}` equals the token's project, compared ordinally. Any other project is the same 403 whether or
  not it exists, so a token cannot probe for names.
- A `read` token: the method is `GET` or `HEAD`, or the route says it is read-only (`ReadOnlyRoute`, which only
  `POST .../environments/{env}/evaluate` carries). A `write` token: any method.
- The route is not root-only (`RootOnlyRoute`): `POST /api/v1/projects` and the three token routes.

`GET /api/v1/projects` is the one route without a `{project}` that a scoped token may call (`OwnProjectListRoute`), and it
returns only that token's project. Any other route without a `{project}` is root-only by that rule. **A new route under
`{project}` is not**: it is open to a write token, and to a read token if it is a `GET`, unless it is marked `RootOnlyRoute`. What
stops one landing unconsidered is a test: `AdminTokenTests` compares every `admin` route with a table of what each token may do, and
fails until the new route is added.

SDK keys are inside that scope on purpose: a write token may create and revoke its project's SDK keys and a read token may
list them (prefixes only). With `TOGGLESLASH_ADMIN_TOKEN` unset the whole admin API is 503, and that includes live scoped
tokens. A scoped token is 403 on every SDK route; an SDK key is 403 on every admin route. The token routes are root-only, but a
token's create and revoke events are in the project's audit trail, so a scoped token can read their name, permission, prefix and expiry there.

Every error body has one shape, from the framework's own 404 and 405 to an unhandled 500:

```json
{ "error": { "code": "forbidden", "message": "This token is valid but may not use this route." } }
```

## Rate limits

`RequestLimiter` (`apps/server/ToggleSlash.Server/Limits`) holds every limit, **in this process's memory**, in one
small class with an injected `TimeProvider`, because the built-in ASP.NET limiter's timers cannot use a fake clock. The
server is one process per database, so that is enough, and **a restart resets the counts**. There is no table and no
shared store. Defaults, variables and proxies are in [`self-hosting.md`](self-hosting.md#rate-limits).

- **Per key:** token buckets on `POST /sdk/v1/evaluate` and `POST /sdk/v1/events`, keyed on the key's id, checked after
  authorization and before the body is read.
- **Failed authentication, per IP:** the authentication handler counts a presented credential that is wrong, and checks
  the count first, so a locked-out IP cannot have a guess confirmed. A missing header and the `503` for an unset admin
  token do not count.
- **Streams, per key:** a slot taken at the top of the route and released by a `using` on every way out.
- **Client IP:** `RemoteIpAddress`. ASP.NET's forwarded headers middleware is installed only when
  `TOGGLESLASH_TRUSTED_PROXIES` lists something, because with an empty list it trusts everyone. IPv6 is grouped by /64.
- **Bounded:** each table has a cap and drops its least recently used entry. Open stream slots cannot be dropped, so past
  the cap a key with no open stream is refused instead. The limiter stores a key's id and a grouped IP in memory, and
  writes neither to the database or a log.

Each answer is a `429` with `Retry-After` in whole seconds, rounded up, and the one error shape. A refused stream has no
refill to compute, so it always says 30 seconds. `Retry-After` is exposed to browsers on the two CORS routes.

## Response headers, body size and timeouts

`Hardening/SecurityHeaders.cs` is the first middleware in the pipeline. It sets its headers in `Response.OnStarting`,
not before `next`, so an exception handler that clears the response, a `401` from the authentication challenge, a `413`
from Kestrel's body cap and the open stream all still carry them. It never writes a CORS header and never touches the
ruleset's `ETag`. `Hardening/RequestLimits.cs` holds the Kestrel limits (a 1 MiB body, 30 s for headers, 2 minutes of
keep-alive) and the request timeout policy (30 s, answered in the error shape). `UseRequestTimeouts` runs after the
routing `WebApplication` puts first, because it reads each endpoint's metadata, and `GET /sdk/v1/stream` opts out with
`DisableRequestTimeout`. A test holds that the stream is the only route that does, and another that exactly `evaluate`
and `events` carry CORS.

The dashboard does the same in `apps/web/src/server.ts` (`src/api/security-headers.server.ts`): one wrapper around
the gate and TanStack Start's handler, so a redirect and the gate's own answers are covered. The nonce is made per
request and handed to TanStack Start in the start context (`handler.fetch(request, { context })`); `getRouter` reads it
with `getGlobalStartContext()`, passes it as `ssr.nonce`, and TanStack writes it on every inline script and style it
renders. No `unsafe-inline` is needed.
Static files are answered by the Workers assets layer before the Worker runs, so `apps/web/public/_headers` gives them
`nosniff` and `no-referrer`; they keep their own caching.

## Admin API and OpenAPI

Under `/api/v1`, every route behind the `admin` policy, so for the root token and, [as above](#auth), scoped tokens. Keys (`projects/{project}`,
`environments/{env}`, `flags/{flag}`) match `^[a-z0-9][a-z0-9_-]{0,63}$` and are fixed once created.

| Route | |
| --- | --- |
| `POST`, `GET /projects`; `GET /projects/{project}` | create (`key`, `name`), list, read |
| `POST`, `GET /projects/{project}/environments`; `GET .../environments/{env}` | create, list, read |
| `PATCH .../environments/{env}` | rename: body `{ "name" }`, trimmed; only the name changes (the key is fixed, and a `key` in the body is ignored like any unknown field); answers 200 with the environment, records one `updated` event, and the ruleset's ETag does not move because a ruleset does not carry the name (a `write` token) |
| `DELETE .../environments/{env}` | delete an environment; 204, or 409 while any of its SDK keys is not revoked (below) (a `write` token) |
| `POST`, `GET /projects/{project}/flags`; `GET`, `PATCH .../flags/{flag}` | create, list (`?tag=`, `?archived=false\|true\|all`, default `false`), read, update metadata |
| `POST .../flags/{flag}/archive`, `.../restore` | archive and restore; both are idempotent |
| `DELETE .../flags/{flag}` | delete an archived flag for good; 204, or 409 while it is not archived or another flag lists it as a prerequisite (below) (a `write` token) |
| `GET`, `PUT .../flags/{flag}/environments/{env}` | read and replace a flag's config in one environment |
| `POST .../flags/{flag}/environments/{env}/toggle` | set `on` and nothing else |
| `POST`, `GET /projects/{project}/environments/{env}/segments`; `GET`, `PUT`, `DELETE .../segments/{segment}` | segment CRUD |
| `POST`, `GET /projects/{project}/tokens`; `DELETE .../tokens/{id}` | scoped API tokens, root token only ([Auth](#auth)) |
| `GET /projects/{project}/environments/{env}/runtime` | what the server serves for the environment: the ruleset's `etag` (the one `GET /sdk/v1/ruleset` gives a server key), `flagCount`, `generatedAt` and `lastChange` (below); nothing about what an SDK has loaded |
| `GET /projects/{project}/environments/{env}/rulesets/{hash}` | what the flags were under a ruleset hash the environment served: `etag`, `firstServedAt`, the flags and segments, no salt; `?flag=<key>` narrows it (below) |
| `POST /projects/{project}/environments/{env}/evaluate` | evaluate a context for any environment, as `POST /sdk/v1/evaluate` does, with no SDK key and nothing recorded; an optional `etag` (a hash the environment served) evaluates against that stored ruleset instead of the current one (below) |
| `GET /projects/{project}/audit`; `GET .../flags/{flag}/history` | the audit trail of a project, and of one flag (below) |

- **Errors** are the single shape above: 400 (`bad_request`) for invalid input, 404 (`not_found`) for an
  unknown project, environment or flag, 409 (`conflict`) for a key that is taken. A flag's key stays
  taken while it is archived, and is free again once the flag is deleted.
- **A flag** has 2 to 100 variations, all one JSON type and none `null` (stricter than the spec, which
  allows `null`), fixed at creation; `name`, `description`, `temporary`, `owner` and `tags` are the
  metadata `PATCH` changes (an `owner` of `""` clears it). Creating one writes a config row in every
  environment of the project, off: `offVariation` 1 and `fallthroughVariation` 0 unless the request
  names others. Creating an environment writes the same default row for every existing flag, archived
  ones included. The `salt` is generated by the server and not exposed.
- **Lifecycle** is a `lifecycle` string on every flag answer, computed on each read and never stored. In this order:
  `archived` when `archivedAt` is set; `active` when any environment counted an evaluation of it on one of the last 7
  UTC days (today included, so `lastEvaluated` is on or after today minus 6); `new` when it was created less than 7
  days ago; otherwise `inactive`. It is one stage for the flag, not one per environment, and there is no code-removal stage.
- **Flag delete** (`DELETE /projects/{project}/flags/{flag}`, a write). It holds the targeting lock and checks and deletes
  in one transaction. It is refused with a 409 unless the flag is archived (recent usage does not block it, because
  archiving already took the flag out of every ruleset), and with a 409 that names each dependent, sorted by key, while any
  other flag of the project, archived or not, lists it as a prerequisite in any environment. It removes the flag and,
  by cascade, its configs and usage counts. The audit trail and the kept rulesets stay, because they address the flag by
  key: its `history` still reads, `rulesets show` for an old hash still answers, and the key can be created again. It
  records one `deleted` flag event (`before` set, `after` null, no environment), and signals nothing: no ruleset
  holds an archived flag, so nothing an SDK has loaded changes, and `lastChange` does not count `deleted`.
- **Runtime read** (`GET /projects/{project}/environments/{env}/runtime`, a read, so a `read` or `write` token of the
  project may call it). It is the server's side only: the server cannot know what an SDK has loaded. `etag` and
  `flagCount` come from the same `RulesetReader` read the ruleset route uses, so `etag` is byte for byte that route's
  `ETag` and archived flags are not counted. `generatedAt` is the server's time. `lastChange` is the newest audit event
  that can change the ruleset, by `OccurredAt` then `Id`, or `null`: `flag_config` and `segment` events of this
  environment, and `flag` events `created`, `archived` and `restored` in the project (they have no environment). A flag
  `updated` does not count (`PATCH` changes metadata the ruleset does not carry), nor do key, token, project and
  environment events, nor an event whose `before` equals its `after`. A toggle or save that changes nothing still bumps
  the config's `version`, which the ruleset carries, so it counts; a segment save that changes nothing counts too,
  though the tag does not move. It returns the actor, type, id and action of the
  event and no snapshot. The audit read and the ruleset read are not one transaction; the audit is read first, so
  the tag is never older than `lastChange`.
- **Environment delete** (`DELETE /projects/{project}/environments/{env}`, a write). It holds the targeting lock and checks
  and deletes in one transaction. It is refused with a 409 that says how many while the environment has any SDK key with no
  `revoked_at`: a live key means something may be running against it, and revoked keys do not block. It removes the
  `environments` row, and every table with a foreign key to it cascades: `flag_environment_configs`, `segments`, `api_keys`
  (only revoked ones are left by then), `flag_usage_daily` and `ruleset_snapshots` lose that environment's rows, and the
  other environments of the project keep theirs. **It keeps the audit trail**: `audit_events` has no foreign key and
  addresses an environment by key, so its history stays readable, and the delete adds one `deleted` event (before the
  environment, after null) and the cascaded rows get none. The last environment of a project may go; flags then have no
  config until an environment is created, and creating one gives every flag an off config. An environment created later
  with the same key is a new one: a new id, off configs, no usage and no snapshots. The ruleset lookup and `runtime` answer
  the environment 404 for it. Nothing is pushed to a running stream: a stream ends at its next wake-up, when its key is no
  longer live, as after a revoke (at the latest the next 25 second heartbeat).
- **Ruleset lookup** (`GET /projects/{project}/environments/{env}/rulesets/{hash}`, a read, so a `read` or `write` token
  of the project may call it; no SDK key can, and it has no CORS). Anything holding the ruleset's `ETag`, such as a trace an application wrote it into, can ask, and this answers
  "what were the flags under that hash". `{hash}` is the tag's lowercase hex without its quotes; anything else is a 404.
  `GET /sdk/v1/ruleset` keeps the exact bytes in `ruleset_snapshots`, keyed by environment and hash, the first time it
  answers 200 with them: it looks first, so a ruleset already kept takes no write lock, and a concurrent first read
  cannot move `firstServedAt` or fail. A failure to keep them is logged and the SDK still gets its flags, so that hash answers 404 until a later 200 of the same body keeps it; an SDK now holding the tag only gets 304s, so a later 200 has to come from another reader. A `304` and a
  flag write store nothing, so a tag `runtime` or the stream has named is a 404 until something read it with a 200, and so
  is the tag of an SDK that has held it since before snapshots existed and only ever gets 304s. The same bytes in two
  environments are two rows; a hash served only in one is a 404 in the other. **A sweep deletes old snapshots** (`Sdk/RulesetRetention.cs`: once at startup, then once an hour; `TOGGLESLASH_RULESET_RETENTION_DAYS`, default 90, `0` keeps every snapshot). In each environment the rows are ordered by `first_served_at` (ties by hash), and a row goes when both hold: its successor, the next row, was first served more than that many days ago, so age counts from when a ruleset stopped being the newest and not from when it first appeared; and its hash is not the environment's current ruleset, because a rollback can make an old body current again without moving `first_served_at`. The newest row has no successor and is never deleted. A pruned hash answers 404, the same as one never served. A failed sweep is logged and leaves the rows; it writes no audit event. The answer is parsed from those bytes and
  leaves out every salt, though the stored bytes hold them. `?flag=<key>` narrows it to that flag and the segments its own
  rules name, not those of its prerequisites; a flag not in that ruleset is a 404.
- **Diagnose at a past hash** (`POST .../environments/{env}/evaluate` with `"etag": "<hash>"`, a read: a `read` or `write` token may call it). It is the
  diagnostic route with a different ruleset: the context is evaluated by the same C# evaluator against the bytes
  `ruleset_snapshots` kept for that hash (`RulesetSnapshot.FromStored`), so the value and reason are what the flag gave
  then, and with no `etag` the current ruleset is read as before. The `etag` is the lookup route's `{hash}`: lowercase
  hex, no quotes. A hash this environment never served, including one from another environment, is a 404; the lookup is
  scoped to the environment in the path. It records nothing: no usage, no audit event, no new snapshot, and the answer
  carries no rules, targets or salt. The SDK's `POST /sdk/v1/evaluate` has no such field and still refuses it with a 400.
- **SDK read API** (`/sdk/v1`, in the OpenAPI document under the `SDK` tag). A key belongs to one
  environment, and the environment is the one it reads; nothing in the URL or body names it.
  - `GET /sdk/v1/ruleset` (server key only; a client key is 403) returns `{ "flags": [...], "segments": [...] }` in
    the shape `docs/evaluation.md` loads, for the key's environment: every flag that is not archived, ordered by
    key, with the `salt` and `version` the evaluator needs, and the environment's segments. It is meant for
    server-side SDKs, which evaluate locally, so it does carry rules, targets and salts: that is why a
    client key, which assumes the key is public, cannot read it.
  - The response has a strong `ETag`, the SHA-256 of the exact bytes sent, so it changes when any flag's
    config, any segment or the set of non-archived flags in the environment changes, and not otherwise
    (a write to another environment, or a read, leaves it alone). `If-None-Match` (an exact tag, a weak
    one, a list, or `*`) gets a `304` with no body. The answer is `Cache-Control: private, no-cache`: a
    cache may keep it but must ask again, and a `304` still needs a valid key.
  - `GET /sdk/v1/stream` (server key only; a client key is 403) is Server-Sent Events for the key's environment.
    It sends `event: connected` with the current ruleset's `ETag`, then `event: changed` with the new one on each
    change, and the client re-fetches the ruleset. The `data` is the tag exactly as the ruleset route's header
    gives it, quotes included, and is all an event carries. A `: keep-alive` comment goes out every 25 seconds.
    - **One server process only.** A write raises `RulesetNotifier`, in this process's memory, after it commits.
      A second instance would not hear it, so a multi-instance deployment needs another bus in its place.
    - The signal carries no tag: each stream holds at most one pending signal, and reads the ruleset when it wakes,
      so a burst or a slow client coalesces to the latest ETag and a writer never waits on a stream. A wake that
      leaves the tag as it was sends nothing. Each stream pays for one ruleset read per wake.
    - A key is checked again before every event and keep-alive, so one revoked mid-stream ends the stream there
      and is told nothing more. Revoking does not itself wake a stream, so that is at most one keep-alive later.
    - A stream ends when the client leaves or the host starts stopping, since Kestrel otherwise waits on open
      requests at shutdown. Either way its subscriber is removed.
    - Writes that signal are the ones the ruleset can see: config, toggle, segment, flag create, archive and restore.
      A flag `PATCH` (its name and description are not in the ruleset) and a new environment (no keys yet) do not.
  - `POST /sdk/v1/evaluate` (server or client key) takes `{ "context": { "key", "attributes" }, "flagKey"? }`
    and returns `{ "flags": { "<key>": { "value", "variationIndex", "reason" } } }`, from the same
    `ToggleSlash.Evaluation` the vectors run against, for the key's environment: every flag that is
    not archived, or only `flagKey`. `reason` is `kind` plus whichever of `ruleIndex`, `flagKey` (the
    failed prerequisite) and `code` apply. It never returns rules, targets, segments, salts, prerequisites or any
    context key but the caller's own. A flag that cannot be evaluated is reported in its own entry
    (`kind: ERROR`, `value: null`) and does not fail the request. An invalid context or body is a `400`
    (checked first, so it is a `400` even for an environment with no flags), and a `flagKey` that does not exist
    or is archived is a `404`.
  - `POST /sdk/v1/events` (server or client key) takes `{ "events": [{ "flag", "variationIndex", "count", "day" }] }`
    (`day` is `yyyy-MM-dd`, UTC) and adds each count to the key's own environment, summing entries that share a
    flag, variation and day. It answers `{ "accepted", "unknownFlags" }`. See **Usage counts** below. It is for
    evaluations the server did not perform (a server SDK evaluating locally): `evaluate` counts its own, so an SDK
    that calls `evaluate` and also reports the result here counts it twice.
  - **CORS is on `evaluate` and `events` only**: any origin, `POST`, the `Authorization` and `Content-Type` headers, a ten-minute
    preflight, and no credentials (the key travels in a header, never a cookie). The preflight is answered without
    a token. The ruleset, the stream and the admin API send no CORS headers, so a browser cannot read them.
  - Each request reads the environment in one transaction, so a ruleset (and its ETag) is one consistent
    snapshot, and there is no cache in the server to go stale: a write is visible on the next read.
- **Usage counts.** `flag_usage_daily` holds one row per environment, flag, variation and UTC day, with a
  `count`. **It is counts only: no evaluation context, context key, attribute or any other end-user data is
  accepted, stored or logged.** An entry that carries a field outside the four above (`contextKey`, `context`,
  `environment` and so on) is refused with a `400`, not stored and not quietly dropped.
  - `POST /sdk/v1/events` upserts additively (`count = count + excluded.count` in one statement), so concurrent
    batches lose no count. The environment comes only from the key, so a batch cannot write to another one, and
    a flag is looked up in the key's own project: one that does not exist there (or at all) is ignored and
    counted in `unknownFlags`. An archived flag still counts. Limits: a body over 128 KiB or more than 1000
    events is a `413` (`payload_too_large`); a malformed body or entry, a `count` outside 1 to 1,000,000,000, a `day` more than
    a day ahead of UTC today or more than 366 days before it, or a `variationIndex` the flag does not have is a `400`, and then **nothing** in the batch is counted.
  - `POST /sdk/v1/evaluate` counts for itself: one for the variation each flag it evaluated served, in the key's
    environment, on today's UTC day. A flag that errored serves no variation and counts nothing. A failure to
    count is logged and never fails the evaluation.
  - `GET /api/v1/projects/{project}/flags/{flag}/usage` (the `admin` policy) returns daily totals for every environment of
    the project, each day with its per-variation counts. `since` and `until` (`yyyy-MM-dd`, inclusive) default to the last 30
    days and may span at most 366.
  - A flag read carries `lastEvaluated`: the latest UTC day with a count in any environment, or `null`. It is a day, not a
    timestamp. It is on the flag read, the list and the flag writes; the audit trail's snapshots leave it out, since it is not part of
    what an admin wrote.
  - Whether a flag is safe to remove is a judgement on top of these numbers and is not computed here.
- **Audit trail.** Every admin write (project, environment, flag, config, segment, SDK key and scoped token, each route
  above that is not a `GET`) adds exactly one `audit_events` row **in the same transaction as the write**: both
  happen or neither does, so a rejected write (400, 404, 409) records nothing and an audit row that cannot be
  written takes its write with it (a 500). A test lists the server's write routes and fails for one without a
  proof, so a new write route cannot skip this. A row holds `occurredAt` (UTC), `actor`, `entityType`
  (`project`, `environment`, `flag`, `flag_config`, `segment`, `api_key`, `admin_token`), `entityId` (the entity's key; a
  config's is `<flag>/<env>`; an SDK key's or a scoped token's is its numeric id), `action` (`created`, `updated`, `toggled`,
  `archived`, `restored`, `revoked`, `deleted`), the `project`, `environment` and `flag` keys it belongs to
  (null when it does not concern one) and `before` and `after`, the entity as the API shows it
  (null before a create and after a delete). The rows carry keys, not ids, so a deleted segment's history
  stays readable. **Nothing private is stored:** the snapshots are the API's own response shapes, so no plain
  SDK key or token, no hash and no salt (a key or a token shows as its prefix); a test checks every column of every row
  for them. The `actor` is `admin` for the root token and `token:<id>` for a scoped one, set by the auth handler on
  the request's database context. **One row per successful
  write request**, even when it changes nothing (archiving an archived flag, revoking a revoked key): `before`
  equals `after` then. Creating an environment or a flag is one row, not one per default config it writes.
- **Reading the trail** takes the `admin` policy, so a scoped token reads its own project's. `GET /projects/{project}/audit` lists a project's events newest first;
  `GET /projects/{project}/flags/{flag}/history` lists one flag's (its metadata, archive state and every
  environment's config); it still answers for a flag that has been deleted. Both take `?environment=` (an environment key; flag-level events have none, so they
  drop out), `?since=` (an ISO 8601 time, inclusive; no zone means UTC), `?limit=` (1 to 200, default 50) and
  `?cursor=`; the audit route also takes `?flag=` (an unknown one is an empty page, because events outlive
  what they describe, where `/history` of an unknown flag is a 404). The body is `{ "events": [...],
  "nextCursor": "..." }`; `nextCursor` is `null` on the last page, and sending it back as `cursor` returns the
  events older than it, so a write made meanwhile never moves a page already handed out.
- **Targeting** is a flag's config in one environment: `on`, `offVariation`, `targets`, `prerequisites`,
  `rules` and `fallthrough`, in the shapes of `docs/evaluation.md`, plus `version`. A `PUT` replaces the
  whole config (an empty array clears a field; leaving out `offVariation` serves `null` when off). The
  `version` it replaces goes in the body or in `If-Match` (`"3"`, `W/"3"` or `3`; if both are sent they must
  agree), and the `ETag` of a `GET` or `PUT` is `"<version>"`. The save is a compare-and-set in one SQL
  statement: a stale or future version is a 409 and changes nothing, and a good one adds 1. `toggle` flips
  `on` without reading or writing any other field, so it cannot undo someone else's edit; it still adds 1
  to `version`, so a `PUT` read before it is stale. Given a `version` it must be current; without one it
  applies to whatever the config is now. New configs start at version 1.
- **What a save is checked against:** variation indexes are in range of the flag's variations (the off
  variation, targets, rules, fallthrough, and each rollout entry); rollout weights are whole numbers
  summing to exactly 100000; context keys are non-empty strings; an unknown field anywhere is a 400
  (stricter than the spec, which ignores them). A prerequisite names another flag of the **same project**,
  and its `variation` is range-checked against *that flag's* variations (the spec leaves it unchecked, since
  an unmet one just never matches). A `segmentMatch` names a segment of the **same environment**. The
  prerequisites a save would leave in this environment must not make a cycle, itself included. Each is a 400
  with a message naming the field.
- **Segments** belong to one environment: `included`, `excluded` and `rules` (attribute clauses only, so no
  `segmentMatch` inside a segment), replaced whole by `PUT`. Their salt is generated and not exposed, like a
  flag's. A segment `DELETE` is a 409 while any flag's rules in that environment still name it, and says
  which flags. Segment writes are compare-and-set like config writes: a `PUT` names the version it read (in
  the body or as `If-Match`), starts at 1 and adds 1, and a stale one is a 409 that changes and records nothing. The
  error code is `version_conflict` here and `conflict` on a config write.
- **Writes take turns.** Config and segment writes hold one in-process lock (`TargetingLock`), because they
  check other rows (flags, segments, the prerequisite graph) before writing and SQLite would let two such
  checks both pass. One process owns one database file, so this is enough; a second server on the same file
  would need the check in the database instead. Reads never take it.
- **OpenAPI:** the built-in generator serves `/openapi/v1.json`, with no token, like `/health`: it
  describes the API and holds nothing private. `apps/server/openapi/v1.json` is that document,
  committed so the TypeScript clients can generate or check against it. A test fails when the two differ;
  regenerate with `TOGGLESLASH_UPDATE_OPENAPI=1 dotnet test apps/server/ToggleSlash.Server.Tests`.

## Evaluation

Evaluation is specified once, in `docs/evaluation.md`, with shared test vectors in
`fixtures/evaluation/`. It is implemented twice, in TypeScript (`packages/engine`) and in C#
(`apps/server/ToggleSlash.Evaluation`), and both implementations must pass the same vectors.

- **Server-side SDKs** fetch the ruleset from the server and evaluate locally. The TypeScript one is `packages/sdk` ([`sdk.md`](sdk.md)).
- **Other clients** (browsers, mobile, anything without an SDK) ask the server, which evaluates (`POST /sdk/v1/evaluate`).

## Dashboard

`apps/web` is not the data owner. It calls the C# server's admin API from server functions
(`src/api/dashboard.ts`), through a typed client in `src/api/client.server.ts`. The server's address is
`TOGGLESLASH_API_URL` and the admin token is `TOGGLESLASH_ADMIN_TOKEN`, both read from the Worker's
environment in `src/api/env.server.ts` and nowhere else. `.server.ts` files are covered by TanStack
Start's import protection, a unit test scans the source for the token, and an e2e test scans every
script the browser loads. The token never reaches the browser.

The list is the route `/`, with the project and environment in the search (`?project=shop&env=staging`),
so a view can be linked. It shows the project's active flags with key, name, tags, temporary, on or off
in the chosen environment and last evaluated; search runs in the browser over the loaded list. Toggle,
create (boolean flags only) and archive (no restore) are server functions that call the admin API; a
toggle sends the version the page read, so a flag that moved on answers 409 and the page says so and
reloads. The server being down, unconfigured or rejecting the token is a page of its own with a retry,
not a crash.

### Sign-in

The dashboard holds the admin token, so nothing in it answers without a session. There is one operator
and no user table: the password is the Worker secret `TOGGLESLASH_OPERATOR_PASSWORD`, and a session is a
stateless cookie, an expiry 12 hours ahead signed with `TOGGLESLASH_SESSION_SECRET` (HMAC-SHA256 through
WebCrypto, verified in constant time, `src/api/auth.server.ts`). With either secret unset or too short,
nobody can sign in and the sign-in page names the variable. Setting them is in
[`self-hosting.md`](self-hosting.md#dashboard-sign-in).

Two layers, and only the second is the security boundary for data:

- **Server functions: refused.** `requireSession` (`src/api/session-middleware.ts`) is registered once, as
  global function middleware in `src/start.ts`, so a server function added later is protected without
  asking. A signed-out call gets a 401 and no data; in a browser its client half then goes to `/sign-in`.
- **Pages: redirected.** The Worker entry (`src/server.ts`, `gate` in `auth.server.ts`) sends a signed-out
  page to `/sign-in?returnTo=...` before anything renders. `returnTo` is untrusted, and only a same-origin
  relative path passes (`src/api/return-path.ts`).

Signing in is a plain form `POST /sign-in` handled in that same Worker entry, not a server function, so no
server function has to be exempt from the middleware. Signing out is a server function, so it needs a
session. A unit test fails if the middleware is not registered on the one Start instance; e2e calls every
server function in the built manifest, signed out, and expects a 401.

### Environments, SDK keys, segments and the audit log

Four more routes take `?project=&env=` like the list; their server functions are in `src/api/operator.ts`
and their client calls in `src/api/operator.server.ts`. The nav in the shell moves between them and keeps
the project and environment.

- **`/environments`**: the project's environments, and create (key and name). The server can now rename and
  delete an environment, and the page does not use either yet (FS-60).
- **`/keys`**: the environment's SDK keys with their prefix, kind and whether revoked. Creating one
  returns the plaintext once. It is held in the keys panel's component state only: it is not in a
  loader, the router cache or the URL, so leaving the page, reloading or dismissing the callout removes it,
  and the server keeps only a hash and the prefix. Revoke asks for a confirm first.
- **`/segments`**: the environment's segments with member and rule counts; edit replaces a segment's
  included and excluded contexts (one per line) and its rules. Rules are edited as JSON text: the browser
  checks only that it is an array, and the server's own validation message is shown for anything else.
  The save carries the version the page read; a stale one (409) keeps the dialog open with the typing in it
  and says to copy what is needed and reload. There is no merge.
  The ticket asked for list and edit, so the page has no create or delete; the admin API has both.
- **`/audit`**: the project's audit log, newest first, 25 events a page, filtered by flag, environment and
  a day (sent as midnight UTC). Paging is by the server's cursor ("Older events", "Back to the newest"),
  kept in the URL so a view can be linked.

### A past ruleset

`/rulesets/$hash?project=&env=` (optional `flag=`) shows what the flags were under a ruleset hash the environment served:
for each flag its on state, off variation, variations, targets, prerequisites, rules and fallthrough, and the segments
its rules name. It is the page a trace backend's link opens (see [`tracing.md`](tracing.md)), so it is behind the normal
sign-in: a signed-out request is redirected to `/sign-in?returnTo=...` before anything renders, and signing in returns
to the same URL. One server function reads `GET .../rulesets/{hash}` with the dashboard's own token, so no token is
in the URL or the browser. A hash the environment never served (or a flag not in it) is a not-found state on the page,
not a crash. The server's answer has no salt and the page shows none.

### Flag detail

`/flags/$flag?project=&env=` is the detail page; the list links to it. One server function
(`loadFlagDetail`) reads the flag, its config in the chosen environment, the project's other flags (for
prerequisites), the newest history (`GET .../history`) and the usage (`GET .../usage`) together. The page
has three parts:

- **Details**: name, description, owner, tags and temporary, saved with `PATCH`.
- **Targeting** (per environment): on or off, the off variation, individual targets (one box of context
  keys per variation), prerequisites, rules (clauses of attribute, operator and values, each serving a
  variation or a rollout) and the fallthrough. The editor works on a *draft* of strings (`src/targeting`,
  pure and unit-tested), so a half-typed percentage is never lost, and sends the whole config with
  `PUT`, since the server replaces the config as a whole. Rollouts are typed as percents, to three
  decimals (the wire weights sum to 100000); a zero entry is not sent. Clause values are comma-separated
  text: a bare `12` or `true` is a number or boolean and `"12"` is the string.
- **History and usage**: read-only, from the audit and usage endpoints.

The `PUT` carries the version the page read. A stale one answers 409: the editor keeps the draft and the
version it read, says someone else changed the flag and says to copy what is needed and reload the page. A
details save on the same page does not replace it, and there is no merge or retry. A 400 from the server's validation is shown at the
field: the server's messages open with the path to the field (`rules[0].rollout ...`), and the editor
matches that opening to its inputs; one with no path shows as a message above the form. A percentage that
is not a number is caught in the browser first.

The flag list reads each flag's configuration for the environment (eight at a time) because the API
has no bulk read of per-environment state. The D1 placeholder table in `apps/web` stays and stays unused.

## Hosting

**Hosting is undecided.** C# does not run on Cloudflare Workers, so the server ships as a container
for self-hosting: `apps/server/Dockerfile` (multi-stage, base images pinned by digest, a non-root user, a
`/data` volume for the SQLite file, a healthcheck on `/health`) and the root `compose.yaml`, described in
[`self-hosting.md`](self-hosting.md). No image is published. The dashboard and the site stay on Workers; the human
steps in `AGENTS.md` (domain, routes, D1, publishing) still apply.

## Build and gate

`apps/server` is four projects: `ToggleSlash.Server` and `ToggleSlash.Server.Tests` (xunit,
`WebApplicationFactory`), and `ToggleSlash.Evaluation` with `ToggleSlash.Evaluation.Tests`. The evaluator is a
class library with no ASP.NET or database dependency; the server references it to evaluate for `POST /sdk/v1/evaluate`. They are wired into Nx with the `@nx/dotnet` plugin. The SDK is pinned to .NET
10.0.402 in `global.json` and `.tool-versions`. `scripts/nx.ts` skips the server, and says so, when
no SDK runs, so a TypeScript-only contributor can still run the gate. A change to `apps/server` needs
the SDK. See `AGENTS.md`.
